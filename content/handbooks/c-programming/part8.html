8.1

Preprocessor Directives — #include, #define, #pragma, stringification

What is the preprocessor?

The preprocessor runs before compilation. It processes lines starting with #: includes files, expands macros, and handles conditional compilation. The output is pure C code that the compiler sees. Think of it as a text substitution engine.

Hindi mein samjhoPreprocessor compilation se pehle run hota hai. # se shuru hone wali lines process karta hai: files include karta hai, macros expand karta hai, conditional compilation handle karta hai. Output pure C code hota hai jo compiler ko milta hai.
💻 C — Preprocessor directives
/* #include — copy file contents here */
#include <stdio.h>     /* System headers: /usr/include/ */
#include "myheader.h"  /* Local headers: current dir first */

/* #define — simple constants */
#define PI 3.14159265
#define MAX_SIZE 1024
#define VERSION "2.0.1"

/* #undef — remove a definition */
#undef PI

/* # (stringification) — turn argument into string */
#define STRINGIFY(x)  #x
printf("%s\n", STRINGIFY(hello));  /* "hello" */

/* ## (token pasting) — join tokens */
#define CONCAT(a, b)  a##b
int CONCAT(my, Var) = 42;  /* int myVar = 42; */

/* Predefined macros */
printf("File: %s\n", __FILE__);
printf("Line: %d\n", __LINE__);
printf("Date: %s\n", __DATE__);
printf("Time: %s\n", __TIME__);
printf("C std: %ld\n", __STDC_VERSION__);  /* 201710L = C17 */
DirectivePurposeExample
#includeCopy file contents#include <stdio.h>
#defineDefine constant/macro#define MAX 100
#undefRemove definition#undef MAX
#pragmaCompiler-specific hints#pragma once
#errorStop compilation#error "Unsupported platform"
#warningEmit warning (GCC)#warning "Deprecated API"
8.2

Macros — Function-like macros, variadic, do-while(0), pitfalls

Function-like macros

Macros can take arguments like functions but are expanded at compile time (zero runtime cost). However, they have dangerous pitfalls: no type checking, multiple evaluation of arguments, and operator precedence issues. Always wrap in parentheses!

Hindi mein samjhoMacros functions jaise arguments le sakte hain par compile time pe expand hote hain (zero runtime cost). Par dangerous pitfalls hain: type checking nahi, arguments multiple baar evaluate, precedence issues. Hamesha parentheses me wrap karo!
💻 C — Macros: good vs dangerous
/* ❌ Dangerous — no parentheses */
#define SQUARE_BAD(x)  x * x
SQUARE_BAD(3 + 1)  /* Expands to: 3 + 1 * 3 + 1 = 7 (not 16!) */

/* ✅ Safe — wrap everything in parentheses */
#define SQUARE(x)  ((x) * (x))
SQUARE(3 + 1)  /* Expands to: ((3 + 1) * (3 + 1)) = 16 ✅ */

/* ❌ Double evaluation problem */
#define MAX(a, b)  ((a) > (b) ? (a) : (b))
MAX(i++, j++)  /* i or j incremented TWICE! */

/* ✅ Use inline functions instead (C99+) */
static inline int max_safe(int a, int b) {
    return a > b ? a : b;
}

/* Multi-statement macro — use do-while(0) */
#define LOG(msg) do { \
    fprintf(stderr, "[%s:%d] %s\n", __FILE__, __LINE__, msg); \
} while(0)

/* Variadic macro (C99+) */
#define DEBUG(fmt, ...) \
    fprintf(stderr, "[DEBUG] " fmt "\n", ##__VA_ARGS__)

DEBUG("x = %d, y = %d", x, y);
Rule of thumb: Use #define for constants and conditional compilation. Use static inline functions for everything that looks like a function. Macros are powerful but dangerous.
8.3

Conditional Compilation — #ifdef, #if, platform detection, feature flags

Conditional compilation

Conditional compilation lets you include/exclude code based on compile-time conditions. This is essential for: cross-platform code, debug/release builds, feature flags, and header include guards.

Hindi mein samjhoConditional compilation se compile-time conditions ke basis pe code include/exclude kar sakte ho. Cross-platform code, debug/release builds, feature flags, aur header include guards ke liye zaroori hai.
💻 C — Conditional compilation
/* Header include guard (classic) */
#ifndef MYHEADER_H
#define MYHEADER_H
/* ... header contents ... */
#endif

/* Modern alternative (non-standard but widely supported) */
#pragma once

/* Debug/Release toggle */
#ifdef DEBUG
    #define LOG(msg) fprintf(stderr, "[DBG] %s\n", msg)
#else
    #define LOG(msg)  /* Expands to nothing in release */
#endif
/* Compile: gcc -DDEBUG program.c  (enables debug) */

/* Platform detection */
#if defined(_WIN32)
    #include <windows.h>
    #define CLEAR "cls"
#elif defined(__linux__)
    #include <unistd.h>
    #define CLEAR "clear"
#elif defined(__APPLE__)
    #include <unistd.h>
    #define CLEAR "clear"
#else
    #error "Unsupported platform!"
#endif

/* Feature flags */
#if __STDC_VERSION__ >= 201112L
    /* C11 features available */
    #define HAS_GENERIC 1
#endif
8.4

Makefiles & Build Systems — Automation, dependencies, multi-file projects

Why Makefiles?

A Makefile automates compilation. Instead of typing long gcc commands, you type make. It tracks file dependencies and only recompiles what changed — critical for large projects with hundreds of files.

Hindi mein samjhoMakefile compilation automate karta hai. Lambe gcc commands ki jagah sirf make likhte ho. Ye file dependencies track karta hai aur sirf changed files recompile karta hai — large projects ke liye zaroori.
💻 Makefile — Production-quality
# Compiler & flags
CC      = gcc
CFLAGS  = -Wall -Wextra -Werror -std=c17 -O2
LDFLAGS =
TARGET  = myapp
SRCS    = main.c utils.c parser.c
OBJS    = $(SRCS:.c=.o)

# Default target
all: $(TARGET)

# Link object files into executable
$(TARGET): $(OBJS)
	$(CC) $(CFLAGS) -o $@ $^ $(LDFLAGS)

# Compile .c → .o (pattern rule)
%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@

# Clean build artifacts
clean:
	rm -f $(OBJS) $(TARGET)

# Debug build
debug: CFLAGS += -g -DDEBUG -O0
debug: clean all

# Dependencies (auto-generated with gcc -MM)
main.o: main.c utils.h parser.h
utils.o: utils.c utils.h
parser.o: parser.c parser.h utils.h

.PHONY: all clean debug
VariableMeaningExample
$@Target namemyapp
$^All prerequisitesmain.o utils.o parser.o
$<First prerequisitemain.c
$*Stem of patternmain (from %.o)
Essential GCC flags: -Wall (all warnings), -Wextra (extra warnings), -Werror (warnings = errors), -g (debug info), -O2 (optimize), -fsanitize=address (memory bugs).
8.5

Multithreading — pthreads, mutex, race conditions, thread safety

POSIX threads (pthreads)

Multithreading lets multiple threads execute concurrently within one process, sharing the same memory space. Race conditions occur when threads access shared data without synchronization. Use mutexes to protect critical sections.

Hindi mein samjhoMultithreading me multiple threads ek process me concurrently execute hote hain, same memory share karte hain. Race conditions tab hoti hain jab threads shared data bina synchronization ke access karte hain. Critical sections protect karne ke liye mutex use karo.
💻 C — pthreads example
#include <pthread.h>
#include <stdio.h>

int counter = 0;
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;

void *increment(void *arg) {
    for (int i = 0; i < 100000; i++) {
        pthread_mutex_lock(&lock);   /* Enter critical section */
        counter++;
        pthread_mutex_unlock(&lock); /* Exit critical section */
    }
    return NULL;
}

int main(void) {
    pthread_t t1, t2;
    pthread_create(&t1, NULL, increment, NULL);
    pthread_create(&t2, NULL, increment, NULL);
    pthread_join(t1, NULL);  /* Wait for t1 */
    pthread_join(t2, NULL);  /* Wait for t2 */
    printf("Counter: %d\n", counter);  /* 200000 ✅ */
    pthread_mutex_destroy(&lock);
    return 0;
}
/* Compile: gcc -pthread program.c -o program */
Without mutex: counter might be 150000, 180000, or any random value. Two threads reading/writing counter simultaneously is a data race — undefined behavior in C11+.
8.6

Advanced Keywords — volatile, restrict, _Generic, _Atomic, _Static_assert

Keywords professionals use

💻 C — Advanced keywords
/* volatile — prevent compiler optimization on this variable
   Used for: hardware registers, signal handlers, memory-mapped I/O */
volatile int *hw_reg = (volatile int *)0x40021000;
/* Compiler will ALWAYS read from this address, never cache it */

/* restrict (C99) — promise that pointer is the ONLY way to access data
   Enables aggressive compiler optimization */
void add_arrays(int *restrict dst,
               const int *restrict a,
               const int *restrict b, int n) {
    for (int i = 0; i < n; i++)
        dst[i] = a[i] + b[i];  /* Compiler can vectorize this! */
}

/* _Generic (C11) — type-based dispatch (poor man's overloading) */
#define type_name(x) _Generic((x), \
    int: "int",           \
    float: "float",       \
    double: "double",     \
    char*: "string",      \
    default: "unknown")

printf("%s\n", type_name(42));     /* "int" */
printf("%s\n", type_name(3.14));  /* "double" */

/* _Atomic (C11) — thread-safe atomic operations */
#include <stdatomic.h>
_Atomic int shared_counter = 0;
atomic_fetch_add(&shared_counter, 1);  /* Thread-safe increment */

/* _Static_assert (C11) — compile-time assertion */
_Static_assert(sizeof(int) == 4, "int must be 4 bytes");
_Static_assert(sizeof(void*) == 8, "Requires 64-bit platform");
KeywordStandardPurposeWhen to use
volatileC89+Prevent optimizationHardware, signals
restrictC99+No pointer aliasingPerformance-critical loops
inlineC99+Inline expansion hintSmall, hot functions
_GenericC11+Type dispatchType-safe macros
_AtomicC11+Thread-safe opsLock-free programming
_Static_assertC11+Compile-time checkPlatform assumptions

C Standards Evolution — C89 → C99 → C11 → C17 → C23, what's new

C standards timeline

C has evolved through multiple ISO standards. Each adds features while maintaining backward compatibility. Most modern code targets C11 or C17. Use -std=c17 for new projects.

Hindi mein samjhoC multiple ISO standards se evolve hua hai. Har standard features add karta hai backward compatibility maintain karke. Modern code C11 ya C17 target karta hai. Naye projects me -std=c17 use karo.
StandardYearKey additionsFlag
C89/C901989Original ANSI standard. Function prototypes.-std=c89
C991999// comments, bool, VLAs, restrict, inline, designated initializers, snprintf-std=c99
C112011_Generic, _Atomic, _Static_assert, threads, anonymous structs/unions-std=c11
C172018Bug fixes only, no new features. Current "safe default."-std=c17
C232024typeof, #embed, constexpr, nullptr, binary literals, auto-std=c23
Recommendation: Use -std=c17 for production code today. Enable -std=c23 for new personal projects to learn modern features. Always use -Wall -Wextra regardless of standard.

Debugging with GDB — Breakpoints, watchpoints, backtrace, core dumps

GDB essential commands

GDB (GNU Debugger) is the industry-standard debugger for C. Compile with -g to include debug symbols. GDB lets you set breakpoints, step through code, inspect variables, and examine crashes with backtraces.

Hindi mein samjhoGDB C ka industry-standard debugger hai. -g flag se compile karo debug symbols include karne ke liye. GDB se breakpoints set kar sakte ho, code step through, variables inspect, aur crashes examine kar sakte ho.
💻 Terminal — GDB session
# Compile with debug info
$ gcc -g -O0 -Wall program.c -o program

# Start GDB
$ gdb ./program

# Essential commands:
(gdb) break main          # Breakpoint at main()
(gdb) break utils.c:42    # Breakpoint at file:line
(gdb) run                 # Start execution
(gdb) next                # Step over (skip into functions)
(gdb) step                # Step into function calls
(gdb) continue            # Continue to next breakpoint
(gdb) print x             # Print variable x
(gdb) print *ptr           # Dereference pointer
(gdb) print arr[0]@10     # Print 10 elements of array
(gdb) backtrace           # Show call stack (crucial for crashes!)
(gdb) watch counter       # Break when variable changes
(gdb) info locals         # Show all local variables
(gdb) quit                # Exit GDB

# Debugging a crash (core dump)
$ ulimit -c unlimited      # Enable core dumps
$ ./program                # Crash → generates core file
$ gdb ./program core       # Analyze the crash
(gdb) backtrace           # See exactly where it crashed

Release workflow (development to production)

Reliable C projects ship through a repeatable workflow: lint/warnings clean, sanitizers clean, tests passing, and release artifacts reproducible. This process reduces regressions and makes debugging production issues much faster.

Hindi mein samjhoReliable C project ka release workflow repeatable hota hai: warnings clean, sanitizers clean, tests pass, aur release artifacts reproducible. Is process se regressions kam hote hain aur production debugging fast hoti hai.
💻 Shell — Professional release pipeline
# 1) Debug build with strict checks
gcc -std=c17 -Wall -Wextra -Werror -g -O0 -fsanitize=address,undefined src/*.c -o app-debug

# 2) Run tests (example)
./app-debug --run-tests

# 3) Static analysis (example tools)
cppcheck --enable=all --inconclusive src/

# 4) Release build
gcc -std=c17 -Wall -Wextra -O2 -DNDEBUG src/*.c -o app

# 5) Smoke test release artifact
./app --version

✏️ Practice Exercises — Part 8 (Difficulty Graded)

🟢 Easy (Do these first)

  1. Create a header file with an include guard. Define 3 macros: a constant (PI), a function-like macro (SQUARE), and a variadic debug macro (DEBUG).
  2. Write a program that uses #ifdef to print different OS names on Windows vs Linux vs Mac. Test with -D_WIN32 and -D__linux__.
  3. Use _Static_assert to verify that sizeof(int) is 4 and sizeof(void*) is 8 on your platform. Observe the compile error on failure.
  4. Write a program that prints __FILE__, __LINE__, __DATE__, __TIME__, and __STDC_VERSION__.

🟡 Medium (Apply your knowledge)

  1. Create a multi-file project (main.c, math_utils.c, math_utils.h, string_utils.c, string_utils.h) and write a Makefile with all, clean, debug targets.
  2. Write a multithreaded program: 4 threads each increment a shared counter 100,000 times. Run with and without mutex. Print final counter and explain the difference.
  3. Use _Generic to create a print_val macro that auto-selects the right printf format for int, float, double, and char*.
  4. Demonstrate the macro double-evaluation bug: write MAX(i++, j++) and show how it increments twice. Then fix it with static inline.

🔴 Hard (Challenge yourself)

  1. Write a complete Makefile with all, clean, debug, release, and test targets. Include automatic dependency tracking with gcc -MMD and -include.
  2. Build a thread-safe counter using _Atomic (no mutex). Benchmark it against the mutex version — measure with clock(). Which is faster? Why?
  3. Create a debug logging library (log.h/log.c) with severity levels (DEBUG, INFO, WARN, ERROR), file/line info, timestamps, and conditional compilation (-DLOG_LEVEL=2).
  4. 🏆 Capstone: Build a complete student records CLI application — multi-file, Makefile, binary file storage, search/sort, error handling, clean ASan report. This is your portfolio project.
