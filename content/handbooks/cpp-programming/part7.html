📖 Part 7 — Memory Management & Smart Pointers

Own Your Memory

Stack vs heap, raw pointers vs smart pointers, unique_ptr, shared_ptr, weak_ptr — master memory ownership and never leak again.

7.1

Stack vs heap — memory layout, new/delete

Where objects live

The stack is fast, automatic memory for local variables (LIFO). The heap is dynamic memory managed with new/delete. Stack objects are destroyed automatically; heap objects require explicit cleanup (or smart pointers).

Hindi mein samjhoStack local variables ke liye fast, automatic memory hai (LIFO). Heap dynamic memory hai jo new/delete se manage hoti hai. Stack objects automatically destroy hote hain; heap objects ko explicit cleanup chahiye (ya smart pointers).
💻 C++ — Stack vs heap
// Stack — automatic lifetime
void stackExample() {
    int x = 42;                   // Stack
    std::string s = "hello";      // Stack (internal buffer may be heap)
    std::vector<int> v = {1,2,3}; // Stack (elements on heap)
}  // x, s, v all destroyed here automatically

// Heap — manual lifetime (DANGEROUS)
void heapExample() {
    int* p = new int(42);        // Allocate on heap
    int* arr = new int[100];     // Array on heap
    // ... use p and arr ...
    delete p;                    // Free single object
    delete[] arr;                // Free array — MUST use []
}

// ❌ Common mistakes
// delete p; delete p;   // Double free!
// p = new int(5);       // Leak old memory!
// Forgot delete         // Memory leak!
FeatureStackHeap
SpeedVery fast (pointer bump)Slower (allocator)
SizeSmall (1-8 MB typical)Large (GBs)
LifetimeAutomatic (scope-based)Manual (new/delete)
FragmentationNonePossible
Thread safetyEach thread has own stackShared — needs sync
Never use raw new/delete in modern C++. Use std::make_unique and std::make_shared instead. Raw memory management is the #1 source of bugs in C++ code.
7.2

std::unique_ptr — exclusive ownership

One owner, automatic cleanup

std::unique_ptr owns a heap object exclusively. When it goes out of scope, it automatically deletes the object. It cannot be copied (only moved). This is the default smart pointer — use it unless you need shared ownership.

Hindi mein samjhostd::unique_ptr heap object ka exclusive owner hai. Scope se bahar jaane pe automatically delete karta hai. Copy nahi ho sakta (sirf move). Ye default smart pointer hai — shared ownership na chahiye to isi ko use karo.
💻 C++ — std::unique_ptr
#include <memory>

// Create with make_unique (preferred — exception safe)
auto p = std::make_unique<int>(42);
std::cout << *p << "\n";  // 42

// Unique ownership — only ONE pointer
// auto p2 = p;       // ❌ ERROR — can't copy!
auto p2 = std::move(p);  // ✅ Transfer ownership
// p is now nullptr

// Custom class
auto dog = std::make_unique<Dog>("Rex", 3);
dog->bark();

// Array of objects
auto arr = std::make_unique<int[]>(100);
arr[0] = 42;

// Factory function returning unique_ptr
std::unique_ptr<Shape> createShape(std::string type) {
    if (type == "circle") return std::make_unique<Circle>(5);
    return std::make_unique<Rectangle>(3, 4);
}

// Custom deleter
auto fileDeleter = [](FILE* f) { if(f) fclose(f); };
std::unique_ptr<FILE, decltype(fileDeleter)>
    file(fopen("data.txt", "r"), fileDeleter);
7.3

std::shared_ptr — reference-counted ownership

Multiple owners, last one cleans up

std::shared_ptr uses reference counting. Multiple shared_ptrs can own the same object. The object is deleted when the last owner is destroyed. Use std::make_shared for efficiency (single allocation).

Hindi mein samjhostd::shared_ptr reference counting use karta hai. Multiple shared_ptrs same object own kar sakte hain. Object tab delete hota hai jab last owner destroy hota hai. Efficiency ke liye std::make_shared use karo (single allocation).
💻 C++ — std::shared_ptr
auto p1 = std::make_shared<int>(42);
std::cout << p1.use_count() << "\n";  // 1

auto p2 = p1;  // ✅ Copy — both own it
std::cout << p1.use_count() << "\n";  // 2

p1.reset();    // p1 releases — count drops to 1
// Object still alive (p2 owns it)

p2.reset();    // p2 releases — count drops to 0
// Object DELETED now

// Shared ownership in data structures
class Node {
public:
    int value;
    std::shared_ptr<Node> next;
    Node(int v) : value(v) {}
};

auto n1 = std::make_shared<Node>(1);
auto n2 = std::make_shared<Node>(2);
n1->next = n2;  // n2 has 2 owners now
shared_ptr overhead: Reference count (atomic increment/decrement) + control block allocation. Prefer unique_ptr when shared ownership isn't needed.
7.4

std::weak_ptr — breaking circular references

Non-owning observer

std::weak_ptr observes a shared_ptr without incrementing the reference count. It breaks circular references that would otherwise leak memory. Use lock() to get a temporary shared_ptr.

Hindi mein samjhostd::weak_ptr shared_ptr ko observe karta hai bina reference count badhaye. Ye circular references todta hai jo nahi to memory leak karenge. lock() se temporary shared_ptr milta hai.
💻 C++ — weak_ptr & circular reference fix
// ❌ Circular reference — MEMORY LEAK!
struct BadNode {
    std::shared_ptr<BadNode> next;  // Both own each other
    ~BadNode() { std::cout << "~BadNode\n"; }
};
{
    auto a = std::make_shared<BadNode>();
    auto b = std::make_shared<BadNode>();
    a->next = b;
    b->next = a;  // Circular! Neither destroyed!
}  // LEAK — destructors never called

// ✅ Fix with weak_ptr
struct GoodNode {
    std::shared_ptr<GoodNode> next;
    std::weak_ptr<GoodNode> prev;  // Non-owning!
    ~GoodNode() { std::cout << "~GoodNode\n"; }
};

// Using weak_ptr
std::weak_ptr<int> weak;
{
    auto shared = std::make_shared<int>(42);
    weak = shared;
    if (auto locked = weak.lock()) {
        std::cout << *locked << "\n";  // 42
    }
}  // shared destroyed
std::cout << weak.expired();  // true — object gone
7.5

Ownership semantics — passing, returning, storing

Who owns what?

The key to safe C++ is clear ownership. Function signatures communicate intent: raw pointer/reference = non-owning, unique_ptr = exclusive transfer, shared_ptr = shared ownership.

Hindi mein samjhoSafe C++ ki key clear ownership hai. Function signatures intent communicate karti hain: raw pointer/reference = non-owning, unique_ptr = exclusive transfer, shared_ptr = shared ownership.
💻 C++ — Ownership patterns
// 1. Factory — return unique_ptr (give ownership)
std::unique_ptr<Widget> createWidget() {
    return std::make_unique<Widget>();
}

// 2. Sink — take unique_ptr (take ownership)
void addWidget(std::unique_ptr<Widget> w) {
    widgets_.push_back(std::move(w));
}

// 3. Use — take raw ptr/ref (don't own)
void process(const Widget& w) {  // Just reading
    w.doWork();
}
void modify(Widget& w) {          // Modifying, not owning
    w.setName("updated");
}

// 4. Share — take shared_ptr (shared ownership)
void observe(std::shared_ptr<Widget> w) {
    observers_.push_back(w);  // Keep alive
}

// 5. Optional — take raw pointer (nullable, non-owning)
void maybeProcess(Widget* w) {
    if (w) w->doWork();
}

7.6

Common memory bugs — leaks, dangling, double-free

Memory bugs and how to prevent them

Memory bugs are the most dangerous in C++: leaks (forgot to free), dangling pointers (use after free), double-free (free twice), buffer overflow (write past end). Smart pointers and STL containers prevent most of these.

Hindi mein samjhoMemory bugs C++ me sabse dangerous hain: leaks (free bhool gaye), dangling pointers (free ke baad use), double-free (do baar free), buffer overflow (end ke baad write). Smart pointers aur STL containers inse bachate hain.
💻 C++ — Memory bugs & fixes
// ❌ Memory leak
void leak() {
    int* p = new int(42);
    if (error) return;  // p never freed!
    delete p;
}
// ✅ Fix: auto p = std::make_unique<int>(42);

// ❌ Dangling pointer
int* dangle() {
    int x = 42;
    return &x;  // x destroyed! Pointer is invalid
}

// ❌ Use after free
int* p = new int(42);
delete p;
*p = 10;  // UNDEFINED BEHAVIOR!

// Tools to detect:
// - Valgrind (Linux)
// - AddressSanitizer: g++ -fsanitize=address
// - Visual Studio CRT Debug Heap

7.7

Custom allocators & placement new

Advanced memory control

Placement new constructs an object at a specific memory address. Custom allocators replace the default heap allocator for STL containers — used in game engines, embedded systems, and high-frequency trading for deterministic performance.

Hindi mein samjhoPlacement new specific memory address pe object construct karta hai. Custom allocators STL containers ke default heap allocator ko replace karte hain — game engines, embedded systems me deterministic performance ke liye use hote hain.
💻 C++ — Placement new
#include <new>  // for placement new

// Pre-allocated buffer
alignas(int) char buffer[sizeof(int) * 10];

// Construct int at specific address
int* p = new (buffer) int(42);
std::cout << *p << "\n";  // 42
// Don't delete! Memory is on stack
p->~int();  // Explicit destructor call

// Pool allocator concept
class PoolAllocator {
    char* pool_;
    size_t offset_ = 0;
public:
    explicit PoolAllocator(size_t size)
        : pool_(new char[size]) {}
    ~PoolAllocator() { delete[] pool_; }

    void* allocate(size_t bytes) {
        void* ptr = pool_ + offset_;
        offset_ += bytes;
        return ptr;
    }
    void reset() { offset_ = 0; }
};

Ownership design playbook (team-level standard)

Most C++ memory bugs are ownership ambiguity bugs. Industrial C++ teams define ownership in API contracts: who creates, who releases, and whether sharing is allowed. If ownership is unclear in code review, design is considered incomplete.

Hindi mein samjhoC++ memory bugs ka major reason hota hai unclear ownership. Professional teams API contracts me clear define karti hain: object ka creator kaun hai, release kaun karega, aur sharing allowed hai ya nahi. Agar ownership clear nahi hai, to design incomplete maana jata hai.

Memory debugging workflow (ASan, UBSan, Valgrind)

A robust workflow is: strict warning build, sanitizer build for fast feedback, stress tests with randomized paths, then Valgrind for deep heap diagnostics when needed. This layered process catches both deterministic and intermittent memory issues.

Hindi mein samjhoBest memory debugging flow: warnings-clean build, sanitizer build for quick feedback, randomized stress runs, aur zarurat ho to Valgrind se deep heap analysis. Is layered process se deterministic aur intermittent dono bugs pakadte hain.
💻 Shell — Memory debug pipeline
# 1) Compile with strict warnings + sanitizers
g++ -std=c++20 -O0 -g -Wall -Wextra -Werror \
  -fsanitize=address,undefined src/*.cpp -o app-debug

# 2) Run regression + stress suite
./app-debug --run-tests
./app-debug --stress --iterations=2000

# 3) Optional deep leak analysis
valgrind --leak-check=full --show-leak-kinds=all ./app-debug --run-tests

# 4) Release build verification
g++ -std=c++20 -O2 -DNDEBUG -Wall -Wextra src/*.cpp -o app
./app --smoke

Memory-safe release checklist

Release readiness for memory-heavy C++ systems requires verifiable guarantees: no leaks in critical paths, no lifetime hazards, no UB reports, and explicit ownership documentation for public interfaces.

Hindi mein samjhoMemory-heavy C++ release ke liye verifiable guarantees chahiye: critical paths me leaks nahi, lifetime hazards nahi, UB reports clean, aur public interfaces me explicit ownership docs.

✏️ Practice Exercises — Part 7 (Difficulty Graded)

🟢 Easy (Do these first)

  1. Create a unique_ptr<Dog>, call methods, then transfer ownership to another unique_ptr with std::move. Verify the original is nullptr.
  2. Create 3 shared_ptr<int> pointing to the same object. Print use_count() after each copy and after each reset().
  3. Write a factory function returning unique_ptr<Shape> for Circle, Rectangle, Triangle types.
  4. Use weak_ptr::lock() to safely access an object that may have been destroyed. Handle the expired case.

🟡 Medium (Apply your knowledge)

  1. Demonstrate the circular reference leak with shared_ptr (two nodes pointing to each other). Fix with weak_ptr. Verify destructors run.
  2. Compile with -fsanitize=address and intentionally trigger a use-after-free, double-free, and memory leak. Read the ASan output.
  3. Implement an ownership transfer chain: createWidget() → processWidget() → storeWidget() using unique_ptr throughout.
  4. Write a unique_ptr with a custom deleter that closes a FILE* handle. Verify the file is closed on scope exit.

🔴 Hard (Challenge yourself)

  1. Implement a simple arena allocator that pre-allocates a buffer and bumps a pointer for each allocation. Add a reset() method.
  2. Build an object pool using unique_ptr with custom deleters that return objects to the pool instead of freeing them.
  3. Use PMR (std::pmr::monotonic_buffer_resource) with a pmr::vector. Compare allocation speed vs default allocator using std::chrono.
  4. Create a shared_ptr cache system: use weak_ptr in a map to cache objects. Return existing shared_ptr if still alive, create new one otherwise.
