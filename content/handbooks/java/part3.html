3.1

Classes & objects — fields, methods, constructors, this

Everything is inside a class

Java is a pure OOP language — every line of code lives inside a class. A class is a blueprint (template), an object is an instance (actual data). Fields store state, methods define behavior, constructors initialize objects. this refers to the current object.

Hindi mein samjhoJava ek pure OOP language hai — har line code class ke andar hoti hai. Class ek blueprint (template) hai, object ek instance (actual data) hai. Fields state store karte hain, methods behavior define karte hain, constructors objects initialize karte hain. this current object ko refer karta hai.
💻 Java — Classes & Objects
// Class definition (blueprint)
public class Student {
    // Fields (state / attributes)
    String name;
    int age;
    double gpa;

    // Constructor (initializer)
    public Student(String name, int age, double gpa) {
        this.name = name;   // this.field = parameter
        this.age = age;
        this.gpa = gpa;
    }

    // Method (behavior)
    public String getGrade() {
        if (gpa >= 9.0) return "A";
        if (gpa >= 8.0) return "B";
        return "C";
    }

    // toString — readable representation
    @Override
    public String toString() {
        return String.format("Student{name='%s', age=%d, gpa=%.1f}",
                             name, age, gpa);
    }
}

// Creating objects (instances)
Student s1 = new Student("Yuvraj", 21, 9.5);
Student s2 = new Student("Alice", 20, 8.7);

// Using objects
System.out.println(s1.name);     // Yuvraj
System.out.println(s1.getGrade()); // A
System.out.println(s1);          // Student{name='Yuvraj', age=21, gpa=9.5}

// Objects are references
Student s3 = s1;    // s3 points to SAME object as s1
s3.age = 22;         // Changes s1.age too!
System.out.println(s1.age); // 22

Stack vs Heap: Primitives and references live on the stack. Objects live on the heap. When you do Student s = new Student(), s is a reference on the stack pointing to the Student object on the heap.
3.2

Access modifiers — public, private, protected, default

Controlling visibility

Java has 4 access levels: public (everywhere), protected (package + subclasses), default/package-private (same package only), private (same class only). Use private fields + public getters/setters for encapsulation — this is the most important OOP principle.

Hindi mein samjhoJava me 4 access levels hain: public (kahin bhi), protected (package + subclasses), default (same package), private (same class). private fields + public getters/setters se encapsulation karo — ye OOP ka sabse important principle hai.
💻 Java — Access Modifiers & Encapsulation
public class BankAccount {
    // ✅ Private fields — encapsulation!
    private String owner;
    private double balance;
    private final String accountId;

    // Constructor
    public BankAccount(String owner, String accountId) {
        this.owner = owner;
        this.accountId = accountId;
        this.balance = 0.0;
    }

    // ✅ Public getter — controlled read access
    public double getBalance() {
        return balance;
    }

    // ✅ Public method with validation
    public void deposit(double amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException("Amount must be positive");
        }
        balance += amount;
    }

    public boolean withdraw(double amount) {
        if (amount > balance) return false;
        balance -= amount;
        return true;
    }

    // No setter for accountId — it's immutable!
    public String getAccountId() { return accountId; }
    public String getOwner() { return owner; }
}

// Usage
BankAccount acc = new BankAccount("Yuvraj", "ACC001");
acc.deposit(1000);
// acc.balance = -500;  // ❌ Compile error! private field
System.out.println(acc.getBalance()); // 1000.0 ✅
ModifierSame ClassSame PackageSubclassEverywhere
public✅✅✅✅
protected✅✅✅❌
default (no keyword)✅✅❌❌
private✅❌❌❌
Rule of thumb: Make fields private, methods public (if part of API) or private (if internal). Never use public fields — it breaks encapsulation and makes refactoring impossible.
3.3

static keyword — static fields, methods, blocks, nested classes

Class-level vs instance-level

static means "belongs to the class, not to instances." Static fields are shared by all objects. Static methods can be called without creating an object (Math.pow()). Static blocks run once when the class is loaded. Use for utility methods, constants, and counters.

Hindi mein samjhostatic ka matlab hai "ye class ka hai, instance ka nahi." Static fields sabhi objects share karte hain. Static methods bina object banaye call ho sakte hain (Math.pow()). Static blocks class load hone pe ek baar run hote hain. Utility methods, constants aur counters ke liye use karo.
💻 Java — static Keyword
public class Student {
    // Static field — shared by ALL instances
    private static int totalStudents = 0;
    public static final String SCHOOL = "MIT"; // Constant

    // Instance fields — unique per object
    private String name;
    private int rollNo;

    // Static block — runs once when class loads
    static {
        System.out.println("Student class loaded!");
    }

    // Constructor
    public Student(String name) {
        this.name = name;
        totalStudents++;
        this.rollNo = totalStudents;
    }

    // Static method — called on CLASS, not object
    public static int getTotalStudents() {
        // ❌ Cannot use 'this' or instance fields here!
        return totalStudents;
    }

    // Instance method — called on object
    public String getInfo() {
        return String.format("#%d: %s (%s)", rollNo, name, SCHOOL);
    }
}

// Usage
Student s1 = new Student("Alice");
Student s2 = new Student("Bob");

// Static access — via class name (preferred)
System.out.println(Student.getTotalStudents()); // 2
System.out.println(Student.SCHOOL);             // MIT

// Instance access
System.out.println(s1.getInfo()); // #1: Alice (MIT)

// ✅ Utility class pattern (all static)
public final class MathUtils {
    private MathUtils() {} // Prevent instantiation

    public static int square(int n) {
        return n * n;
    }
    public static boolean isEven(int n) {
        return n % 2 == 0;
    }
}
// MathUtils.square(5) → 25

3.4

final keyword — final variables, methods, classes

Making things immutable

final means "cannot be changed". Final variables = constants (cannot reassign). Final methods = cannot override in subclasses. Final classes = cannot extend (no inheritance). Use static final for compile-time constants. Final references can still mutate the object's contents!

Hindi mein samjhofinal ka matlab hai "change nahi ho sakta". Final variables = constants (reassign nahi). Final methods = subclasses me override nahi. Final classes = extend nahi. static final compile-time constants ke liye use karo. Final references me object ka content change ho sakta hai!
💻 Java — final Keyword
// ✅ final variable — constant
final int MAX_SIZE = 100;
// MAX_SIZE = 200;  // ❌ Compile error!

// ✅ static final — class constant
public static final double PI = 3.14159265358979;
public static final String APP_NAME = "MyApp";

// ⚠️ final reference — object can still be modified!
final List<String> names = new ArrayList<>();
names.add("Alice");   // ✅ Modifying contents is OK
// names = new ArrayList<>(); // ❌ Reassigning reference is NOT OK

// final parameter — cannot reassign inside method
public void process(final String data) {
    // data = "new";  // ❌ Compile error!
    System.out.println(data.toUpperCase()); // ✅ Can read
}

// ✅ final method — cannot be overridden
public class Base {
    public final void criticalMethod() {
        System.out.println("Cannot override this!");
    }
}

// ✅ final class — cannot be extended
public final class ImmutableConfig {
    private final String dbUrl;
    private final int port;

    public ImmutableConfig(String dbUrl, int port) {
        this.dbUrl = dbUrl;
        this.port = port;
    }
    public String getDbUrl() { return dbUrl; }
    public int getPort() { return port; }
}
// class SubConfig extends ImmutableConfig {} // ❌ Cannot extend!

3.5

Constructors — default, parameterized, copy, this(), chaining

Initializing objects properly

A constructor is a special method with the same name as the class, no return type. Java provides a default no-arg constructor only if you don't define any. Use this() to chain constructors. Copy constructors create a new object from an existing one.

Hindi mein samjhoConstructor ek special method hai jiska naam class jaisa hota hai, koi return type nahi. Agar koi constructor nahi banaya to Java default no-arg constructor deta hai. this() se constructors chain karo. Copy constructor existing object se naya object banata hai.
💻 Java — Constructors
public class Product {
    private String name;
    private double price;
    private int quantity;

    // No-arg constructor
    public Product() {
        this("Unknown", 0.0, 0); // Chain to full constructor
    }

    // Partial constructor
    public Product(String name) {
        this(name, 0.0, 0);  // Chain with defaults
    }

    // Full constructor
    public Product(String name, double price, int quantity) {
        this.name = name;
        this.price = price;
        this.quantity = quantity;
    }

    // Copy constructor
    public Product(Product other) {
        this(other.name, other.price, other.quantity);
    }

    // Getters & Setters
    public String getName() { return name; }
    public double getPrice() { return price; }
    public int getQuantity() { return quantity; }
    public void setPrice(double price) { this.price = price; }

    @Override
    public String toString() {
        return String.format("%s ($%.2f x %d)", name, price, quantity);
    }
}

// Usage — multiple ways to create
Product p1 = new Product();                  // Unknown ($0.00 x 0)
Product p2 = new Product("Laptop");          // Laptop ($0.00 x 0)
Product p3 = new Product("Phone", 999.0, 5); // Phone ($999.00 x 5)
Product p4 = new Product(p3);               // Copy of Phone
Constructor TypeSignatureUse case
Default (implicit)Product()Only if no constructors defined
No-argProduct()Create with defaults
ParameterizedProduct(name, price)Create with specific values

Important: this() must be the first statement in a constructor. If you define ANY constructor, Java stops providing the default no-arg constructor — you must define it explicitly if needed.
3.6

Method overloading — same name, different parameters

Multiple methods, one name

Overloading = same method name, different parameter list (type, count, or order). Return type alone does NOT count. Resolved at compile time (static dispatch). Common in constructors, utility methods (Math.abs() has 4 overloads), and println().

Hindi mein samjhoOverloading = same method name, different parameters (type, count, ya order). Sirf return type se overload nahi hota. Compile time pe resolve hota hai. Constructors, utility methods (Math.abs() me 4 overloads hain), aur println() me common hai.
💻 Java — Method Overloading
public class Calculator {
    // Overloaded add methods
    public int add(int a, int b) {
        return a + b;
    }
    public double add(double a, double b) {
        return a + b;
    }
    public int add(int a, int b, int c) {
        return a + b + c;
    }
    public String add(String a, String b) {
        return a + b; // String concatenation
    }
}

Calculator calc = new Calculator();
calc.add(1, 2);         // calls int version → 3
calc.add(1.5, 2.5);     // calls double version → 4.0
calc.add(1, 2, 3);      // calls 3-arg version → 6
calc.add("Hello", " World"); // calls String version

// ✅ Varargs — variable-length arguments
public int sum(int... numbers) {  // int[] internally
    int total = 0;
    for (int n : numbers) total += n;
    return total;
}
sum(1, 2);            // 3
sum(1, 2, 3, 4, 5);  // 15
sum();                // 0

✅ Different param typesadd(int, int) vs add(double, double)Types differ
✅ Different param countadd(int, int) vs add(int, int, int)Count differs
✅ Different param orderf(int, String) vs f(String, int)Order differs

3.7

Records (Java 16+) — immutable data carriers, DTOs

Concise immutable data classes

Records (Java 16+) auto-generate constructor, getters, equals(), hashCode(), and toString(). They're immutable — fields are final. Perfect for DTOs, API responses, value objects. Records can have custom methods but cannot extend classes.

Hindi mein samjhoRecords (Java 16+) automatically constructor, getters, equals(), hashCode(), aur toString() generate karte hain. Ye immutable hain — fields final hain. DTOs, API responses, value objects ke liye perfect hain.
💻 Java — Records
// ❌ Old way — 50+ lines of boilerplate!
public class PointOld {
    private final int x, y;
    public PointOld(int x, int y) { this.x = x; this.y = y; }
    public int x() { return x; }
    public int y() { return y; }
    // + equals(), hashCode(), toString()... 😴
}

// ✅ Record — one line! (Java 16+)
public record Point(int x, int y) {}

// Auto-generates:
// - Constructor: Point(int x, int y)
// - Getters: x(), y()  (no "get" prefix!)
// - equals(), hashCode(), toString()

Point p = new Point(3, 4);
System.out.println(p.x());   // 3 (accessor, not getX)
System.out.println(p.y());   // 4
System.out.println(p);       // Point[x=3, y=4]

// Records with custom methods
public record Rectangle(double width, double height) {
    // Custom method
    public double area() { return width * height; }
    public double perimeter() { return 2 * (width + height); }

    // Compact constructor — validation
    public Rectangle {
        if (width <= 0 || height <= 0) {
            throw new IllegalArgumentException("Dimensions must be positive");
        }
    }
}

// Record for API response (DTO pattern)
public record ApiResponse<T>(int status, String message, T data) {}

var response = new ApiResponse<>(200, "OK", List.of("a", "b"));
